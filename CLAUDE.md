# specreview

Review specs where they are rendered. Teams keep Markdown in each repo's `docs/`; specreview publishes each repo as a site on one hub the org hosts on its own Cloudflare account and domain, where readers comment on selected text and product signs pages off; the sign-off shows on linked GitHub issues as a label. Open source and self-hosted: the hub (`packages/hub`) is AGPL-3.0-only with its own `LICENSE`, everything else MIT under the root `LICENSE`; `pnpm check:packages` enforces each package's `license` field (decided 9 Oct 2026, #21). Plan and domain model: issue #1.

Every change: an issue first, then a test plan on the issue before code, a branch, a PR, the full local gate before each push, and review before merge.

## Branches

Gitflow. `develop` is the integration branch and the GitHub default; `main` takes releases only. Branches are `<prefix>/<issue>-<slug>` (prefix one of feature, bugfix, hotfix, chore, fix, ci, infra, refactor, docs) or `release/<x.y.z>`, cut from `develop`; always pass `--base develop` to `gh pr create`. Husky refuses env files, `.dev.vars` and `.pem` files at commit, non-conventional commit messages, and pushes to `develop`, `main` or a badly named branch (tags pass), and runs `pnpm typecheck` before every push. Hooks are installed by `pnpm install` and can be skipped, so CI (`.github/workflows/ci.yml`, one `verify` job) runs `scripts/check-packages.mjs` before installing (it reads only `package.json` files, and install is when a package's scripts would run), checks the branch name, the commit messages and that no secrets file is added on every PR, then runs `lint:check`, `format:check`, `typecheck`, `test` and `build`, and fails if `publish/dist/` differs from a fresh build.

Releases (#84): `release/<x.y.z>` from `develop`, a PR into `main` merged with a merge commit, the tag `v<x.y.z>` on that merge commit (never moved: hubs pin the commit it points to), a GitHub release, then `main` merged back into `develop` by a PR from `chore/<issue>-back-merge-<x.y.z>` cut from `main` (CI refuses `main` as a PR branch), with a merge commit; the steps are in `CONTRIBUTING.md`. The README, the org template and `examples/publish-docs.yml` say to pin a release tag's commit, and `run.sh` prints the release a pinned commit is (`git tag --points-at`, `v*`) or warns that it is none, refusing nothing. Upgrading a hub moves `specreview.commit` and, by hand until #148, the two pins in each product repo's `docs.yml`.

Solo repo for now: loop step 12 (team review) is N/A.

## Commands

```
pnpm install --frozen-lockfile
pnpm lint            # autofix
pnpm lint:check      # assert clean; CI uses this, never lint
pnpm format:check
pnpm check:packages  # fails if a package lacks typecheck, test or build (pnpm -r would skip it), or runs a script on install
pnpm typecheck       # tsc in every package, separate from any bundler
pnpm test            # vitest in every package; the hub runs in workerd
pnpm build
pnpm --filter @specreview/hub test   # one package; names: @specreview/hub, @specreview/site, @specreview/shared, @specreview/action, @jadedm/specreview (cli)

# One file or one test. The package scripts wrap vitest (the hub's builds shared first, the site's
# builds shared and then itself); `exec vitest run` skips that, which is fine because tests alias shared to src/.
pnpm --filter @specreview/shared exec vitest run src/text.test.ts
pnpm --filter @specreview/hub exec vitest run --project worker test/routing.test.ts -t "must be JSON"
pnpm --filter @specreview/hub exec vitest run --project deploy deploy/setup.test.ts   # Node, not workerd
pnpm --filter @specreview/site exec vitest run src/build/sidebar.test.ts
```

The hub has two Vitest projects: `worker` (`test/**`, in workerd with a fresh D1 migrated by `test/apply-migrations.ts`) and `deploy` (`deploy/**`, plain Node). Without `--project` Vitest picks the project that owns the path; naming the other project finds no test files and exits 1. The site's `test/build.test.ts` runs the built `dist/build/cli.js` on throwaway git repos, so build the site package before running it directly.

Lint, in `.ts` and `.mts` files: `console` other than `console.error` is an error outside `packages/cli`, `any` is an error, and unused variables are errors (only an unused argument may be silenced with a leading `_`). Prettier is checked in CI, so run `pnpm format` before a push.

`pnpm-workspace.yaml` sets `minimumReleaseAge: 1440` (#79): a new or refreshed dependency resolves only to versions at least a day old; installs from the lockfile are unchanged.

`@specreview/shared` resolves types from `src/` and runtime from `dist/`; the hub's and site's Vitest configs alias it to `src/` so tests run before the build, and `pnpm -r build` builds it first. `happy-dom` is a root dev dependency on purpose: installed in one package only, pnpm makes a second Vitest variant and the hub's Workers pool fails with "Vitest failed to find the runner" (a stale `node_modules` can keep the old variant; reinstall clean).

Library packages build with `tsconfig.build.json`, which leaves tests out of `dist/`; Vitest looks in `src/` (the hub and site also in `test/`). `action` and `cli` run under Node from `dist/`, so they use `NodeNext` resolution and relative imports need `.js` extensions.

## Site build (packages/site)

- `specreview-site build --repo <name> [--docs docs] [--out .specreview] [--exclude <path>]...`, run from inside the product repo. `--exclude` (#88, at most 20) leaves paths in the docs folder out of the site: `*` within one name, `**` as a whole segment across folders, a plain path is a file or a whole folder (a trailing `/` changes nothing), no leading `-`, case-sensitive (`isExcludePattern` in `@specreview/shared` checks the shape for the build and the hub); excluded files, links and submodules are skipped by the symlink check and deleted from the export before any other check, and history versions under an excluded path are dropped. The build action takes them as `exclude`, one per line, passed as separate arguments; the admin page's add-site form as "Leave out", comma separated, at most 10 of 100 characters, written into the workflow's `exclude: |` block. It builds the docs folder **as committed at HEAD**: `git archive` exports it to a temp folder, so no uncommitted, untracked or gitignored file can be published and the manifest's commit is exactly what was built. A throwaway VitePress root (config and theme from this package's `dist/`) builds the export; Vue resolves to this package's copy because a product repo has no `node_modules`. A link into an excluded path is not a dead link (#101): a markdown-it core rule (`excludedLinks` in `src/build/config.ts`) resolves each relative or docs-root link against its page, and when `excludedBy` matches the file it names, the page VitePress resolves it to (`.md`/`.html` stripped, `index` after a trailing slash, plus `.md`) or that path itself, rewrites it to the same target from the docs folder's top and records it by `deadLinkKey`; `ignoreDeadLinks` excuses those keys, unless a docs-root link outside the excluded paths has the same key (VitePress keys `/a.html` and `/a.md` alike), so every other dead link (a near miss included) still fails; a link to a missing file inside an excluded path is excused too, since it is a link into that path. A link to exactly a published prototype file, or to a folder with its slash whose `index.html` is one (`prototypeLink`; an excluded file is never published, so exclusion wins), is instead written with the site's base, `target="_blank"` and `rel="noopener"` (#113; a new tab since #126, as the prototype hostname has no way back, and no opener for its unsanitized script); any other link into a prototype path (a folder without its slash, a clean URL) stays excused and reaches the 404 page, since the hub redirects only those two forms: VitePress leaves a prototype link alone (no base added, no dead-link check, no in-site routing), its click opens a new tab, and the hub's docs hostname answers a path the live manifest lists as a prototype with a 302 to the same path and query on `protoHostname` (after the usual sign-in and read check; an anonymous visitor of a public site gets it with the site's `public, max-age=60`; a hub without a prototype hostname answers the 404 page). On a public site the redirect leads to the prototype hostname's sign-in, which an anonymous visitor may not pass, and it tells anyone which prototype paths exist (their names only). The build refuses a prototype path the site also serves (its file, `.html` or folder index, compared by exact name against the built files, so a case-insensitive disk refuses no more than R2 would; #120) and one under `assets/` (the hub keeps an older build's `assets/` files), either of which would shadow the redirect. On the site an excused link reaches the build's 404 page with its "Go to <site title>" link. Prototypes (#111, epic #110): `--prototypes <path>` (repeatable, the `--exclude` pattern rules, at most 20; the build action's `prototypes:` input, one per line) leaves the matched paths out of the site as `--exclude` does (the #101 link rule and history treat them as left out too) and copies them as `git archive` exports them (byte for byte unless `.gitattributes` asks for a conversion), from the same export as the site (set aside before the exclusion pass), into `<out>/proto/<path in the docs folder>`; a path both excluded and listed stays out. Refused, from git's file list rather than the disk: a symlink or submodule there, a name outside the router grammar or starting `_api`, `_history` or `_signin`, two paths differing only in case, a pattern matching no committed file (one whose matches are all excluded counts as matched), and set-aside files that differ from git's list (a case clash between folders on a case-insensitive disk, or an `export-ignore`). The manifest gains `prototypes`, one `{ path, hash }` per file (sha256 of the bytes, ascending, checked by `isManifest`; absent without prototypes). After the build the whole bundle (site, history, prototypes) must be at most 5000 files and 25 MB uploaded, counting each part's multipart framing as 256 bytes plus twice its name. `isManifest` refuses prototype paths the router would not take (leading dot, reserved first segment) and two differing only in case. The uploader sends `proto/<path>` parts; the hub accepts them from #112. A build with prototypes adds a generated page (#114, `src/build/prototypes-page.ts`): `prototypes.md` written into the export after the author-page checks, last in the sidebar as "Prototypes", one row per published `.html` prototype (so an excluded one is not listed), grouped under a heading per folder (the docs folder's top first, with none; a heading drops the leading folders every prototype folder shares, keeping at least its own name, #136: `product/prototypes/admin` beside `product/prototypes/clipper` reads `admin`), sorted by path, each the file's title as a browser finds it (one forward scan, so a file of any size or shape costs one pass: comments are stepped over, as are raw-text elements such as `<script>`, `<style>` and `<textarea>`, a `<template>`, and inline `<svg>` or `<math>` with their own titles; inside the title only `</title` counts, so tag-like words in it stay text; quoted attributes may hold `>`, and attributes are read as a browser reads them (#122: a quote opens a value only where one starts, after an attribute's `=` and spaces; in a value without quotes a quote or `=` is text; whitespace is HTML's); inside a skipped `<svg>`, `<math>` or `<template>` the scan walks the tags, counting nested ones of the same name and stepping over comments, CDATA, attribute values and self-closing tags (a `/` inside a value does not make one), and inside a template raw text children too, which end at their first closer as raw text elements do elsewhere (in an svg or math a `<style>` or `<script>` holds markup, as in a browser; at most 120 characters; the file name when there is none or it is blank) with every ASCII punctuation mark backslash-escaped, linking to the docs-root path (`folder/` for an `index.html`) so the #113 rule sends it to the prototype hostname. With prototypes, a docs page `prototypes.md`, `prototypes/index.md` or `prototypes.html.md`, case aside, or any file in a `prototypes.html/` or `prototypes.md/` folder, is refused, naming the generated page, and the page is written with exclusive create, so it never replaces a docs file; without them, `prototypes.md` is an ordinary page.

## Publishing (#5)

- `POST /_publish/<repo>` takes one build as `multipart/form-data` (`site/<path>`, `history/<commit>/<path>.md`, and `proto/<path>` prototypes, #112; at most 25 MB counted as it arrives, so the body, its parts and the form fit in a Worker's memory; 5000 files). It is outside the reader paths, so the deploy has Access bypass exactly `/_publish/*`; the hub authenticates it with the GitHub Actions OIDC token in `Authorization: Bearer` (`src/github-oidc.ts`).
- The token must come from GitHub (issuer, keys, RS256), name the hub's origin as audience, and carry exactly the site's `repositoryId` and the hub's `ownerId` (ids authorize, names only route: a renamed repo keeps its id), `repository`, `workflow_ref` = `<org>/<repo>/<workflow>@refs/heads/<branch>`, `ref`, `event_name` = `push` (pull requests, `pull_request_target`, `workflow_run`, dispatch and schedule are refused), and the site's `environment` when set. Its `jti` is recorded in D1 (`publish_tokens`) before anything is written: a token publishes once, and if it cannot be recorded nothing is published; rows older than a day are deleted. If GitHub's keys cannot be fetched the answer is 503, which the uploader retries.
- The hub checks the bundle whole (manifest valid and naming the token's `sha`, every page's HTML, history exactly as the manifest lists it with matching hashes), writes it under a fresh version `<sha>-<run_id>-<run_attempt>-<random>`, records the build's own assets in `<repo>/meta/<version>/assets.json`, copies the previous version's own assets it lacks (one generation, so open tabs keep loading), and moves `current.json` by compare-and-set on its etag (`If-None-Match: *` for the first). A run older than the live one (run ids compared as `BigInt`) is not promoted: 409 `SUPERSEDED`. History keys are shared across versions, so history is written only after the pointer moves, and `_history/` serves a file only if the live manifest lists that commit and path with the file's hash (the hash is of the stored bytes, so a byte-order mark is kept). Known limits: between the pointer moving and history being written, new history entries 404 for a moment, and if the write fails they stay 404 until a rerun publishes again; an older run that went live just before a newer one can still write its history after it, harmless while history bytes come from `git show` and are the same for every build of a commit.
- Config per site: `branch`, `repositoryId`, `workflow`, optional `environment`; hub `ownerId`. Repo names may not start with `_`.
- Actions: `build/` (installs only the root, the site build and shared from the action's own checkout, `--filter . --filter "@specreview/site..."`, and runs the site build; no token; #79) and `publish/` (runs only the committed `publish/dist/publish.mjs`, bundled from `packages/action` with no dependencies; CI fails if it differs from its source). `examples/publish-docs.yml` is the two-job workflow: build with no `id-token`, upload the artifact (pushes only, kept one day; #78), publish with `id-token: write`, actions pinned by SHA, `concurrency` per ref. The uploader makes text from the hub, the network and its inputs inert before printing it (#79: control characters become spaces, every `::` and `##` is broken up, since GitHub reads `::` at a line start and `##[` anywhere as workflow commands; the site build's CLI breaks them up too, keeping line breaks). The uploader takes the hub as an exact https origin, refuses redirects, gets a fresh token per attempt, retries 5xx and network errors, and never prints the token.
- Smoke: the hub smoke server (`SMOKE_SHA_FILE=<file with the commit>`) also stubs GitHub's keys and serves a stand-in Actions token endpoint on 127.0.0.1:8799; run `publish/dist/publish.mjs` with `ACTIONS_ID_TOKEN_REQUEST_URL=http://127.0.0.1:8799/token?x=1`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN=smoke`, `INPUT_HUB=http://127.0.0.1:8797`, `INPUT_REPO`, `INPUT_OUT`.

## Deploying a hub (#9)

- `packages/hub/deploy/` (Node, bundled by `pnpm --filter @specreview/hub build` to `dist/deploy.mjs`): `setup`, `deploy`, `secret` and `workflow-token`, each with `--org <dir>` (the organisation's `specreview.config.json` and `hub.json`) and `--token-file` (a Cloudflare token read at each call, passed to wrangler only as `CLOUDFLARE_API_TOKEN`). `examples/org/` is the template for an organisation's private hub repo (#55): a blank `hub.json` (empty `accountId`, `hostname` and `adminHostname`, which `loadOrg` refuses until filled in, default names, none of the ids setup writes; the deploy tests use `deploy/fixtures/finished-hub.json` for the same org after setup), `run.sh` that clones specreview fresh into a temporary folder for every run, deleted after, and refuses a pinned commit not on one of its branches (#78: nothing from an earlier run is reused, since what is built there gets the token, and GitHub would serve a fork-only commit asked for by name), and runs one command (it refuses the all-zero placeholder commit); `run.sh check-docs <product repo> <site build options>` (#92, no token) instead builds the site package and runs the site build in that repo into `<repo>/.specreview-check`, refused if it already exists and deleted after, so a newcomer sees what their docs folder is refused for before installing (`deploy/run.test.ts` runs the real `run.sh` with git, pnpm and node stubbed on PATH); a template `specreview.config.json` with `configRepo` and no sites (#92: sites come from the admin page; its README says how to find `ownerId`, and `repositoryId` for a site added by hand); and `.github/workflows/apply.yml`, which runs `apply.sh` on pushes to `main` and by hand, never for pull requests, with `contents: write`, one at a time and never cancelled, actions pinned by SHA. `apply.sh` refuses unless `GITHUB_REF` is main and `CLOUDFLARE_API_TOKEN` is set, moves to the newest `origin/main` (a queued run must see ids an earlier run recorded), sets the bot's git identity through `GIT_AUTHOR_*` and `GIT_COMMITTER_*` (a fresh runner has none, and the rebase rewrites the commit), writes the token to a mode-600 file deleted on exit and unsets it (run.sh and everything it runs are still trusted with it), runs `setup --apply` then (only if setup succeeded) `deploy`, skipping the deploy when saving `hub.json` after setup rebased onto a `main` that changed anything else (#78: the files are then not what setup applied; the push that brought them queues its own run, unless it was made with a `GITHUB_TOKEN`), and after each, whether or not it succeeded, commits `hub.json` alone as the Actions bot and pushes, rebasing once onto a newer main; if that still fails it prints `hub.json` to the log, since its ids exist nowhere else; the exit code is the first failure. Pushes with `GITHUB_TOKEN` start no workflow, so this does not loop. A repository secret reaches workflows on any branch and a writer can edit the workflow on theirs, so anyone with write access to the hub repo can get the Cloudflare token; the README says to give write access only to the hub's administrators. Every push to `main` also runs the repo's own `apply.sh` with the token, and the hub's GitHub App commits there, so the app's key reaches it too, Workflows permission or not (#76). The README lists what the paid plans add: an environment limited to `main` holding the token (Team) and required reviewers on it (Enterprise Cloud, for private repos); a ruleset requiring pull requests would refuse `apply.sh`'s and the readers and approvers form's commits. The tests run with `user.useConfigOnly` so git cannot guess an identity, as on a runner. Tests: `deploy/apply.test.ts` runs the real `apply.sh` in throwaway repos (a bare repo as GitHub, a stub `run.sh`); on a Mac with an endpoint scanner, a case can stall for minutes in process start-up, so each case has a long limit. The README lists two tokens (#66): the install token, used from a laptop for the first install (it creates the one-time PIN login), `workflow-token` and repairs, never stored in GitHub; and the workflow token, which `workflow-token --out <new file>` creates (`deploy/workflow-token.ts`): the kind from the token's own prefix (`cfat_` account-owned, `cfut_` user, unprefixed asked of Cloudflare's verify endpoints user first, other `cf*_` prefixes refused), the hostname's zone found as setup finds it, permission groups from the catalogue (one call; it is not paged) by exact name and scope, not marked `is_selectable: false` (Cloudflare documents the field for account catalogues only; missing or doubled refuses), named `specreview apply <hostname> <UTC time to the second>` within Cloudflare's 120 characters (#78), created with an account policy and a zone policy; a create with no answer, a reply that is not JSON, a 5xx or an answer with neither id nor value says a token of that name may exist (`WORKFLOW_PERMISSIONS`: identity providers Read, R2 Write whatever the config), the value written only to `--out`, reserved before any call with exclusive create and mode 600 (an existing file or symlink refused and untouched) and removed on any failure (even when closing it fails); the value is written with `writeFileSync` on that descriptor, which finishes or throws, and a value that cannot be written names the created token to delete. A test compares the README's workflow list with `WORKFLOW_PERMISSIONS`. A 403 from the Cloudflare API names the permission the call needed (`permissionFor` in `deploy/cloudflare.ts`, Read for GET and Write otherwise). setup's last line after `--apply` is "hub.json updated; commit it" only when hub.json changed, otherwise "done; hub.json unchanged".
- setup reads everything before creating anything and stops, changing nothing, on any refusal. It tracks resources by the ids it writes into `hub.json` right after creating each one, never by name, so a run that fails between creates resumes; a create whose answer is lost leaves a resource setup will not adopt until it is recorded in `hub.json` by hand (its id, or `bucket.created: true` for the bucket; the refusal says which). An app adopted that way gets its audience recorded by the next run. Access uses reusable policies (`/access/policies`; per-app policies cannot be added to new apps): an allow policy whose include list setup keeps exactly what the config implies (team domains, readers, admins, `team` emails and approvers, an email a domain rule already covers left out; email and email-domain rules only), on the hostname's app limited to the one-time PIN login, and a bypass-everyone policy on an app for `<hostname>/_publish/*`. While any site is public (#20) it also keeps a bypass app over `<hostname>/<repo>/*` for those sites, with its own bypass policy, and adds their `/_api/*`, `/_history/*` and `/_signin` paths as destinations of the hostname's app; it recognises paths of that shape for any repo name, so a site removed from the config is cleaned up rather than refused. Updating the hostname's app keeps all its other settings (session length, cookies, CORS); Access may cap the destinations one app holds (three per public site), which is unchecked. setup refuses, rather than overwrites, a policy with another decision, `require` or `exclude` rules, non-email rules or more than one app using it, and an app with another type, another covered hostname or path (`destinations`, `self_hosted_domains`; beyond the public-site paths above) or a non-public destination, other policies, another audience, or login methods other than the one-time PIN. Other policy settings (purpose justification, isolation, session length) are not inspected. setup also refuses (#78) any Access app not recorded in `hub.json` that covers the docs or admin hostname or a path under either, case aside, including a wildcard host with a path (Access applies the most specific match, so it could open or shadow part of the hub; an app's `self_hosted_domains` count only when it has no `destinations`, as Cloudflare ignores them otherwise; a bare `*.example.com` app and bookmarks are left alone), refuses WARP sign-in (`allow_authenticate_via_warp`) on the hostname's and the admin app, and notes, without refusing, CORS origins, preflight bypass or framing on the hostname's app. With `adminHostname` (#75) it checks that hostname as it does the docs one (zone active, no other DNS record, no other Worker's custom domain), keeps a reusable allow policy `specreview <adminHostname> admins` whose include list is exactly the config's `admins`, and an app on the admin hostname limited to the one-time PIN login and that policy (`access.adminPolicyId`, `adminAppId`, `adminAud`), refusing an app of its own that covers more, has another audience or policies, other login methods, or lets other origins read it (`cors_headers` allowing origins, `options_preflight_bypass`); removing `adminHostname` deletes both, refusing while the app covers more than one hostname or has other policies, or the policy is on another app (the hostname then stays on the Worker until removed in the dashboard). It validates the config with a placeholder admin audience, and `deployable` requires the admin ids only when `adminHostname` is set. deploy adds the admin hostname as a second custom-domain route and waits for each hostname on its own. With `protoHostname` (#116, `specs-proto.<domain>` by convention) setup checks that hostname as it does the others and keeps, through the same helper as the admin pair (`ownHostname`), a reusable policy `specreview <protoHostname> readers` whose include list is exactly the main policy's (its own policy, since the main policy must stay on one app) and an app on exactly that hostname with one-time PIN and that policy only (`access.protoPolicyId`, `protoAppId`, `protoAud`), refused as the admin app is when it covers more, has another audience or policies, other login methods, CORS or WARP; ids that alias another of the hub's policies or apps are refused; a recorded one that is gone is refused while the hostname is set and forgotten while removing it; removal deletes the app, then the policy. The stray-app scan counts it as a hub hostname; public-site bypass and destinations stay on the docs hostname. `deployable` requires its ids, `workerConfigOf` passes `hostname`, `protoHostname` and `accessProtoAud`, deploy adds a third route and waits for it too.
- Logo (#33, `deploy/brand.ts`): `brand.logo` in the org's config names a PNG or WebP beside it, checked by its signature, at most 256 KB. deploy reads it once, uploads it first as `_brand/logo-<sha256>.<ext>` (`wrangler r2 object put`) and adds the key to `hub.json` `brand.keys` at once, then deploys the Worker naming that key and records it as `brand.logoKey` as soon as `wrangler deploy` succeeds (the new Worker is live then, whatever the wait says). Only after the wait succeeds does it delete every other key in `brand.keys`; a failed delete is a warning and stays listed for the next deploy, and a failed migration, deploy or wait deletes nothing. No `brand.logo` deletes the last one.
- deploy validates the merged config with the hub's own `problemsIn` (the Access team domain and audience come from `hub.json`, nowhere else), writes a wrangler config with absolute paths and the pinned `compatibility_date` and cron, applies D1 migrations, deploys, then waits for the hostname to answer with the Access redirect. Each poll tries the machine's resolver first; if that fails, it asks the zone's own nameservers (`deploy/direct-dns.ts`: walks up to the enclosing zone, follows CNAMEs, probes every address with the hostname as TLS name, one address family per probe with Node's family autoselection off, and any probe that throws or rejects counts as no answer from that address, #100), within a 10 s budget, because the local resolver and public resolvers can hold a "no such name" cached from before the record existed (#27). A hub found only that way is reported with how to flush the resolver; a timeout says the Worker is deployed and gives the same advice. `--dry-run` needs no token and no network. `secret` sets only the GitHub secrets (`GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY`, or the two personal tokens) and refuses before the first deploy.
- Tests: the Vitest project `deploy` (Node) beside `worker` (workerd), `pnpm --filter @specreview/hub exec vitest run --project deploy`. `deploy/test-helpers.ts` is a stand-in for the Cloudflare API with two items per page; one test runs a real `wrangler deploy --dry-run` on `examples/org` with every proxy pointed at a closed port.

## Hub (packages/hub)

One hub per org: each org deploys its own Worker in its own Cloudflare account, on its own domain, behind one Access application. Each of the org's repos is a site at `/<repo>/`.

- Config: `SPECREVIEW_CONFIG` is the JSON of the org's `specreview.config.json`: `org`, `accessTeamDomain`, `accessAud` (the hub's one Access application), `admins`, an optional `teamLabel`, an optional `brand` (#33: `name`, and `logo` as `{ key, type }` naming the stored file; the org's own file has `logo` as a file name, which setup and deploy both resolve before validating, through `workerConfigOf` in `deploy/org.ts`), and per site `repo` (bare name), `teamDomains`, optional `team` (exact emails of people who are team individually, #91), `approvers` (exact emails or `@domain`, anywhere, #91), `readers`, `ticketRepo` (a repo of the same org), optional `teamLabel`, optional `visibility` (`public` or `private`, default `private`; #20). It is validated before anything else; any problem answers 500 `CONFIG_INVALID` to every request, `/` included. Rules (`src/config.ts`; `test/config.test.ts` breaks one rule per case): lowercase names, unique repos, sites sharing a ticket repo have the same team, no public mail domain as a team or reader domain (a blocklist of common providers and their regional domains, best effort), `team` lowercase unique emails, approvers lowercase exact emails or `@domain` with no public mail domain (named by position), readers lowercase exact emails or `@domain`, an email in any of these lists or in `admins` holding before its `@` only what an address may hold unquoted (RFC 5322 atext and letters and digits of any script, and dots, no leading, trailing or doubled dot, at most 64 characters before the `@` and 254 in all; #135; a signed-in person's own email is not held to this, so someone whose address cannot be listed exactly, a quoted one say, still gets in through an `@domain` entry or a team domain), admins non-empty and unique, `sites` a list, empty for a hub just installed (#92; the root index then tells an admin "No sites yet" with a link to the admin page's Sites tab, 200, and anyone else gets the no-access page; the Sites and People tabs say so too), `brand.name` by the `teamLabel` rules and `brand.logo.key` `_brand/logo-<sha256>.png|webp` with the matching type, `teamLabel` 1 to 40 code points with something visible, no control, unassigned or private-use characters, separators or bidi overrides, no outer spaces, no `@` and not `You` or `Reader` (after NFKC folding and removing invisible characters; lookalike letters from other scripts are not caught), no unknown keys. Problems name reader entries by position (`sites[2].readers[1]`), never by value, since they are logged (#77). `readers` is interim until the admin page (#12) keeps them in D1 and keeps Access in sync.
- Identifiers: URL paths and store keys use the bare repo; database rows use `<org>/<repo>` (`site.key`); GitHub calls use `<org>/<ticketRepo>`.
- Paths: `/<repo>/` then `_api/...`, `_history/<40-hex commit>/<path>.md`, or a page. `/<repo>` without a slash, a doubled slash, and anything not under an exact configured repo are 404 before any identity check. `_signin` is reserved like `_api` and `_history` (the site build refuses a page named so). Besides `/_publish/<repo>` (Publishing, above), the exception is `GET /` and `HEAD /` (#43, `src/root.ts`): after sign-in, an index page listing only the sites the caller may read, however many (#45: one site is listed, not redirected to), under the heading "<organisation> docs", each row its live index page's title and a line with its page count, pages in review and ready to build, and build date (#52; the repo name and no line if the site is unpublished, has no titled index page, cannot be read, or the store does not answer within 2 s; the title but no line if the page statuses cannot be read from D1 within 2 s; HEAD reads nothing); none is a 403 page naming no site and reading nothing from the store, which names the signed-in email and links Access's `/cdn-cgi/access/logout` to sign in with another. Both wear the house style (#48): true greys, the system font, no script, one hashed inline style; the top bar's contents share the content's column (#50). Segments are `[A-Za-z0-9._~-]`, split and never decoded; URL parsing has already resolved dot segments.
- Public sites (#20): on a site with `visibility: "public"`, a page or asset (`GET`/`HEAD`) with no Access assertion at all is served to anyone, `public, max-age=60`; a present but invalid assertion is still 401, and `_api`, `_history` and every write still need a sign-in, so a wrong Access rule cannot open a private site or any API. Every HTML page of a public site gets `<meta name="specreview-visibility" content="public">` in its head (HTMLRewriter), and the review panel then shows nothing until `_api/me` answers. `/<repo>/_signin` (behind Access, not linked from the page) answers a signed-in visitor with a 302 to `/<repo>/`. setup keeps Access to match: while any site is public, a bypass app (`access.publicAppId`, policy `access.publicPolicyId`) covers `<host>/<repo>/*` for each public site, and the hostname's own app adds `<host>/<repo>/_api/*`, `/_history/*` and `/_signin` as destinations, so those requests keep the audience the hub trusts. It grows the main app before changing the bypass and shrinks it after, deletes both when no site is public, and forgets (not refuses) a recorded public app or policy that is gone. The root stays behind Access.
- Access: the token's audience is the hub's. Role per site: `approver` by exact email or `@domain` in `approvers` (anywhere; an approver has the team's view and powers, resolving anyone's thread and moving page status, besides signing off; #91), else `team` by team domain or by exact email in `team`, else `reader` by exact email or `@domain` (exact match on the part after `@`), otherwise `none`. Sites sharing a ticket repo must have the same team domains; `team` and approvers may differ, each seeing only their own site's tickets. Token emails are trimmed and lowercased. A signed-in caller who may not read a site gets 403 on every routable path of it, before anything is read from the store or the database (malformed paths are 404 and a missing token 401 first, except a public site's pages; #20).
- What readers see (`src/identity.ts`): never another person's email or a ticket title. In comments (authors, reply authors, `resolvedBy`) a stored email becomes `You` (with `mine: true`), the site's `teamLabel` (site, then hub, then `<org> team`) for anyone who is team on the site now, or `Reader`; page status `changedBy` gets the same labels without `mine`. `resolvedPr` is team only. Tickets lose `title` and `url`. `GET _api/pages` gives the UI the snapshot's `commit` and each page's title, hash, issues and sections (`id`, `title`, `text` only, for everyone), plus history (authors, PRs) for the team only; it replaces reading `manifest.json`. Team and approvers see emails, ticket titles and links, PRs and history. Every ticket's labels are filtered to our three exact status labels. `GET _api/brand` gives everyone who may read the site the org's `name` (or null) and whether there is a logo; `GET _api/brand/logo` serves the stored image with its type, nosniff and `default-src 'none'` (404 without one). The site shows them at the right of the nav bar (`src/theme/brand.ts`, a Vue component in the nav slot; logo only on a phone), as a link to the hub's index `/` with `target="_self"` so VitePress's router does not keep the click inside the site's base (#53).
- Pages: served from the store at `<repo>/v/<version>/`: `a/b` tries `a/b.html`, `a/b/index.html`, then the file `a/b`, except that a path ending in an extension from the content-type table tries the file first (`a/e.js`, then `a/e.js.html`, then `a/e.js/index.html`); a dot elsewhere (`release-1.2`) is a clean URL; a trailing slash is the directory index. A path with no file (and `manifest.json`) gets the build's own `404.html` with status 404, the protected headers and the manifest CSP (#17); a build without one, and every `_api` or `_history` path, gets the JSON 404. GET and HEAD only. Content types from a fixed table; anything else downloads (`octet-stream`, `attachment`). Pages and assets are `private, no-store` (a public site's, served without a sign-in, `public, max-age=60`; #20), with nosniff, `same-origin` referrer, frame `DENY`, and for HTML the CSP from the manifest (default `default-src 'self'`); every other file gets `default-src 'none'; sandbox`, and SVG and PDF (`application/pdf`, #97) also download (`attachment`; an `<img>` of an SVG still renders), so a file opened on its own runs nothing (#77). The exception to `no-store` is a content-addressed asset (#104, `isContentAddressed` in `@specreview/shared`: under `assets/`, Vite's `<name>.<8-character hash>.js|css` but never a page chunk `<page>.md.<hash>[.lean].js`, which holds the page's text, or `.mjs` under `assets/mermaid-<x.y.z>/`; asset URLs carry no version, and the hub takes a name of that shape as a content hash without hashing the bytes), which is `private, max-age=31536000, immutable` for everyone, a public site's anonymous visitor included (never `public`, so no shared cache holds it). History (GET only) is the same with `default-src 'none'`; API and error responses are `no-store` with `default-src 'none'`.
- Store (`src/store.ts`, binding `SITES`, R2): `<repo>/current.json` names the live version (`<sha>-<run_id>-<run_attempt>-<random>` with its `runId`, written last by a publish), `<repo>/v/<version>/` holds the build and `manifest.json`, `<repo>/history/<commit>/<path>.md` old pages, `<repo>/p/<version>/<path>` prototypes (#112, read only on the prototype hostname), and `_brand/logo-<sha256>.<png|webp>` the organisation's logo (#33; repo names may not start with `_`, so no site's files can share that prefix). A request or a reconcile takes one snapshot (pointer then manifest) and uses it throughout (`ctx.snapshot()`). Commits are 40-hex (SHA-1 repos only). Pointers are cached 10 s per repo, single flight, failures not cached; manifests by repo and version, never evicted (#9 measures it). No pointer is 503 `SITE_NOT_PUBLISHED` and links nothing; a bad pointer or manifest is 503 `SITE_BROKEN` and fails the label sync for its ticket repo, so nothing is cleared. Any store error is a generic 503 `STORAGE_UNAVAILABLE`. Without the binding, any route that reads the store answers 500 `STORE_NOT_CONFIGURED`. `manifest.json` is never served as a page: its history entries (authors, PRs) are for the team.
- Sites of one org share an origin. Script in one repo's built pages runs with the viewer's sign-in on every site of the hub: for a viewer of both, it can comment, resolve threads, sign pages off as ready, and read team-only history on another repo. The origin check and the CSP do not stop it, and a `Referer` is forgeable within an origin. Accepted: every site is the same org's docs, published from its own repos. A separate subdomain per site would be the fix. Orgs are separated by separate deployments.
- Write caps (`src/comment-rules.ts`, `src/rate-limit.ts`): 30 writes a minute per site and email (`write_log`), 200 open threads a page and 20 per author, 200 replies a thread and 20 per author, resolved threads listed newest first up to 300. Open threads are always all listed, since an unlisted one would block ready with nothing to resolve.
- Every table is keyed by `site` (the ticket cache by ticket repo, since sites can share one), and every query filters on it; replies reference threads by `(site, thread_id)`. Ticket labels are computed per ticket repo across every site that files tickets there, and the hub creates its three labels in a repo the first time it needs them. A cron every 5 minutes (`wrangler.jsonc`) reconciles each ticket repo on its own, repairing failed or overlapping syncs and clearing labels from tickets no page links. A failed sync, from the cron or after a page change, logs one line per ticket repo naming the step and GitHub's answer (`label sync failed for <org>/<repo>: GET /issues/52 -> 500 (GitHub had an error)`), never the token or a response body beyond GitHub's JSON `message` (or, for a redirect, the hub's own message naming its status).
- GitHub (#6, `src/github-app.ts`, `src/github-auth.ts`): every call to GitHub's API goes through `githubFetch` (`src/github-fetch.ts`, #77), which never follows a redirect (GitHub answers one for a renamed or transferred repo or issue): 301, 302, 303, 307 and 308 read as a 502 whose message names the status and nothing of the target, never as a 404 (a 404 means done for a label removal and "not installed" for an app lookup); the test stand-in records any call made without `redirect: 'manual'` and `test/apply-migrations.ts` fails the test. Which identity the hub uses, first match wins: the GitHub App in the `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` secrets, the app created on the admin page and stored in D1 (#56; read at most once a minute per isolate; one its key cannot open gives no token, never the personal tokens), the personal tokens. As an app, the hub signs an app JWT (RS256, `iat` a minute back, 9 minutes' life, reused while over a minute is left) looks up the installation on each ticket repo (`GET /repos/<org>/<repo>/installation`, cached an hour; "not installed" is asked again after a minute) and mints a token for that one repo, Issues read for reads and Issues write for labels, cached per repo and purpose until 5 minutes before it expires, single flight. The key may be PKCS#1 (as GitHub downloads it) or PKCS#8; it is wrapped to PKCS#8 before import (workerd would take PKCS#1 bytes as PKCS#8, the standard does not). A 401 on a lookup, or a 401 or 404 on a mint, starts over once with a new JWT and installation; a 401 on an issues or labels call drops that token and retries once with a new one. With neither app secret set the two personal tokens are used; with only one, no token at all (one log line naming the missing secret). Caches are per isolate. Failures give no token, which callers treat as "unavailable", and a log line with no key or token (a broken key: imported once, logged once).
- Admin page (#56, `src/admin.ts`): served only on its own hostname (#75; `hub.json` `adminHostname`, a sibling of the docs hostname by convention), never on the docs sites' origin: the Worker config carries `hostname`, `adminHostname` and `accessAdminAud` together (`config.admin`), a request whose hostname is exactly `adminHostname` is verified against `accessAdminAud` and may reach only `/_admin` and `/_admin/*` (`/` redirects 302 to `/_admin/`, anything else 404 before sign-in), and on the docs hostname a GET or HEAD of an admin path redirects 308 to the same path and query on the admin hostname while any other method 404s; without `adminHostname` there is no admin page (the docs hostname answers a 404 page saying it needs one). The add-site form writes the docs origin (`https://<hostname>`) into a new site's workflow. On the admin hostname, three tabs (#133), each its own address under a tab bar of links (the current one `aria-current="page"`), no script: People at `/_admin/` (who reads and approves, one box per site, approvers, team members, readers in that order, each saying what it allows; a `POST /_admin/access` answers with this tab and its result in a `role="status"` box at the top, with the outcome's status; a change that did not go through shows its result alone with a link back, without reading the lists from GitHub again), Sites at `/_admin/sites` (the sites with their ticket repo, and the add-site form, its second step `/_admin/sites?repo=`), GitHub App at `/_admin/github` (the app or its create form, ticket repos, Forget; the manifest return and Forget redirect here); without a usable app, People and Sites say so and link the GitHub App tab. Each tab's `<title>` names it before the organisation; only the GitHub App tab's CSP allows posting a form to github.com. Routes are per method (`GET` and `POST /_admin/sites`). `/_admin/` for the config's `admins` (`/_admin` redirects 308 to it, #62; a non-admin opening any of the three tabs gets a 403 page naming their email with Access's sign-out link, while posts and the GitHub return answer the JSON 403; unknown `/_admin/*` paths 404 before sign-in; its own Access app, admins only, covers the admin hostname).
